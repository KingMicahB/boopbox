# BoopBox device v2: parts and wiring plan

v1 (ESP32-Audio-Kit, see `device/WIRING.md` on the `claude/device-companion-wiring-zsacpn`
branch) ran out of pins and had no Wi-Fi, Bluetooth audio or screen to speak of. v2 is built
from separate modules around two chips, each with one radio job.

> Nothing here has been built yet. Pin facts for the ESP32-C5 come from Espressif's
> ESP32-C5-DevKitC-1 user guide (v1.2 header table) and ESP-IDF `soc_caps.h`. **Strapping pin
> levels are not confirmed yet**: read the ESP32-C5 datasheet, section *Boot Configurations*,
> before the first wire goes on (Phase 0).

## What v2 must do

| Requirement | How |
|---|---|
| Everything v1 did: card slot + sticker spot, two knobs, speaker, SD card, on-board battery | Same PN532 readers, encoders, speaker and LiPo |
| Wi-Fi, **5 GHz**, good connection | ESP32-C5: dual-band 2.4 + 5 GHz Wi-Fi 6, external antenna |
| Download on demand, playback starts at once | Chunked download to SD, plays from the first chunk (see [Downloads](#downloads)) |
| Bluetooth headphones | Second chip: ESP32 (original) as A2DP **source** |
| Box as a Bluetooth speaker for the phone | Same second chip as A2DP **sink**. Not at the same time as headphones (agreed) |
| Phone app controls the box | BLE on the ESP32-C5 |
| Headphone jack, at the same time as Bluetooth headphones | PCM5102A DAC fed from the same digital stream |
| No noise | Audio stays digital (I2S) until each output; separate clean DAC supply |
| Colour screen | SSD1351 1.5" 128 × 128 colour OLED |
| USB-C | One USB-C socket on the case: charging + flashing / logs |
| Speaker (mono) | One MAX98357A and one speaker |

### Why two chips

Only the original ESP32 does Classic Bluetooth (A2DP, needed for headphones and for "box as
speaker"). The ESP32-C5 is the only ESP32 with 5 GHz Wi-Fi, and it does BLE only. Putting
Wi-Fi downloads and Bluetooth audio on separate chips also means they never share a radio,
which is the usual cause of stutter. With Wi-Fi on 5 GHz they don't even share a band.

## Power

```
 USB-C (case) --VBUS--> CHARGER (power path) --SYS--> SWITCH --> VSYS (3.0-4.2 V)
       |                    |                                  |-- MAX98357A amp VIN
       |                   BAT                                 |-- 3.3 V BUCK-BOOST --> 3V3 rail:
       |                    |                                  |     C5, WROVER, OLED, both PN532,
       |                  LiPo --100k--+--100k-- GND           |     SD, MCP23017, encoders
       |                               |                       |-- 3V3 rail --ferrite--100uF--> DAC VIN
       |                        C5 GPIO5 (battery level)
       +--D+/D- --> C5 GPIO14 / GPIO13 (USB, 12 Mbit/s)
```

* The switch sits **after** the charger, so the battery charges with the box switched off.
* Amps run straight from the battery: no 5 V boost, so no boost noise. Expect roughly 1.5–2 W per
  speaker instead of 3 W; plenty for a toddler box.
* Both dev boards are fed on their `3V3` pins from the buck-boost. Their own USB sockets stay
  unplugged in the finished box (the C5's USB comes from the case socket through GPIO 13 / 14).
* The battery divider draws about 20 µA, negligible.

## ESP32-C5 pin map

The DevKitC-1-N8R8 headers carry GPIO 0–14 and 23–28. Not available or kept free:

| GPIO | Why |
|---|---|
| 15–22 | Flash and PSRAM |
| 11, 12 | UART0, wired to the board's USB-UART chip |
| 13, 14 | USB D- / D+ to the case socket |
| 27 | On-board RGB LED, and a strapping pin |
| 28 | BOOT button, strapping pin (low at reset = download mode) |

Strapping pins (2, 3, 7, 25, 26) are only used for **outputs into high-impedance inputs**
(I2S clocks and data, OLED DC), so nothing outside pulls them at reset.

| GPIO | Signal | Goes to |
|---|---|---|
| 6 | SPI SCK | OLED `SCL/CLK`, reader A `SCK`, SD `CLK` |
| 24 | SPI MOSI | OLED `SDA/DIN`, reader A `MOSI`, SD `DI/MOSI` |
| 23 | SPI MISO | reader A `MISO`, SD `DO/MISO` |
| 8 | OLED CS | OLED `CS` |
| 9 | Reader A CS | reader A `SS` |
| 10 | SD CS | SD `CS` |
| 2 | OLED DC | OLED `DC` (strap pin, output only) |
| 0 | I2C SDA | reader B, MCP23017, WROVER GPIO21 |
| 1 | I2C SCL | reader B, MCP23017, WROVER GPIO22 |
| 25 | I2S BCK (C5 is clock master) | DAC `BCK`, amp `BCLK`, WROVER GPIO26 |
| 26 | I2S WS | DAC `LCK`, amp `LRC`, WROVER GPIO25 |
| 7 | I2S data out | DAC `DIN`, amp `DIN`, WROVER GPIO33 |
| 4 | I2S data in | WROVER GPIO27 (phone audio in speaker mode) |
| 5 | Battery level (ADC1_CH4) | battery divider midpoint, 100 nF to GND |
| 3 | spare | strap pin: output only |
| `RST` | | OLED `RST` (resets with the C5) |

The ESP32-C5 has one general-purpose SPI bus and one I2S controller, which is why the screen,
reader A and SD share a bus and the I2S runs full duplex on shared clocks.

## Bluetooth board (ESP32-WROVER-IE) pin map

| GPIO | Signal | Goes to |
|---|---|---|
| 26 | I2S BCK in (slave) | C5 GPIO25 |
| 25 | I2S WS in | C5 GPIO26 |
| 33 | I2S data in (audio to headphones) | C5 GPIO7 |
| 27 | I2S data out (phone audio to the box) | C5 GPIO4 |
| 21 | I2C SDA (slave, address 0x30: commands and status) | I2C bus |
| 22 | I2C SCL | I2C bus |
| `EN` | Reset | MCP23017 `GPB0` |

Avoid GPIO 0, 2, 5, 12, 15 (strapping), 6–11 (flash) and 16, 17 (PSRAM) on the WROVER.

## MCP23017 (address 0x20)

| Pin | Direction | Goes to |
|---|---|---|
| `GPA0` `GPA1` `GPA2` | in | Knob 1 `CLK`, `DT`, `SW` (volume, play/pause) |
| `GPA3` `GPA4` `GPA5` | in | Knob 2 `CLK`, `DT`, `SW` (back/forward) |
| `GPA6` | in | Jack switch contact (plugged in = speakers mute) |
| `GPA7` | **out** | Amp mute: gate of the amp's MOSFET |
| `GPB0` | out | WROVER `EN` |
| `GPB1` | out | DAC `XSMT` (soft mute) |
| `GPB2`, `GPB3` | in | Charger `CHG` and `PGOOD` (charging icon) |
| `GPB4`–`GPB6` | in | spare buttons |
| `RESET` / `A0`–`A2` | | 3V3 / GND, as in v1 |

`GPA7` and `GPB7` are output-only on current MCP23017 chips, so they only carry outputs. The
expander is polled over I2C (no interrupt pin: the only free C5 pins are strapping pins, and an
interrupt held low at a reset could send the C5 into download mode).

I2C addresses: MCP23017 0x20, reader B 0x24 (fixed), WROVER 0x30. Keep the bus short (under
about 20 cm in total).

## Audio

```
 SD / Wi-Fi ---> C5 decoder, volume limit ---I2S out---+--> DAC ------> jack
                                                       +--> amp ---> speaker
                                                       +--> WROVER ---> BT headphones
 Phone --BT--> WROVER ---I2S in---> C5 (same path to DAC and amps)
```

* The I2S bus runs at a fixed 44.1 kHz, 16-bit stereo. 48 kHz files are resampled on the C5. In
  speaker mode the WROVER drops or repeats a sample now and then, as the phone's clock and the
  box's never quite match.
* **Modes:** normal (speaker, or the jack when something is plugged in); Bluetooth headphones
  (speakers muted, jack can play too); box as phone speaker (headphones unavailable).
* Bluetooth headphones play about 0.15–0.25 s behind the jack. Fine for one listener; two
  listeners at once will hear the offset. Fixing it would need a second I2S data line, and the
  C5 has no pins left for one.
* The phone sees two names: **BoopBox** (BLE, the app) and **BoopBox Speaker** (Classic, only
  pairable while a grown-up turns speaker mode on, so no stranger's phone can take over).

### Amp (mono) and mute

The speaker is mono. With its `SD` pin left as it comes, the MAX98357A plays (L+R)/2, so both
channels of a stereo file come out of the one speaker.

The `SD` pin also has a small N-MOSFET to GND, its gate on MCP `GPA7` with a 100 kΩ pull-up to
3V3. At power-on the expander pins float, the pull-up turns the MOSFET on, the amp stays shut
down, and there is no pop until the firmware is ready.

Headphones (jack and Bluetooth) stay stereo: that comes from the DAC and the Bluetooth chip, not
the speaker.

### Noise

* No analog audio crosses between boards: every link is I2S until the DAC and the amps.
* DAC on its own filtered supply (ferrite + 100 µF), its own ground wire back to the
  buck-boost, as far from the antennas as the case allows.
* DAC board solder jumpers: `SCK` to GND (internal clock), `FMT` low (I2S), `XSMT` **not**
  bridged high, wired to MCP `GPB1` with 10 kΩ to GND so the DAC is muted at power-on.
* Amp `GAIN` pin to `VIN` = 6 dB, the lowest that still gets full volume from a digital signal;
  less gain is less hiss.
* All grounds meet at one point (the buck-boost output).

## Antennas

* **Wi-Fi:** Espressif's DevKitC-1 comes with a PCB antenna only. Either mount the board with its
  antenna end at the top of the case, at least 3 cm from metal, the battery, the speaker magnet
  and both readers; or use a board built on the **ESP32-C5-WROOM-1U** module (U.FL socket) with a
  dual-band flexible antenna stuck inside the case wall. The second is the better connection.
* **Bluetooth:** WROVER-IE with its flexible antenna at the **opposite** end of the case from the
  Wi-Fi antenna, 5–10 cm apart or more.
* No metallic paint or foil over either antenna.
* 5 GHz reaches less far through walls than 2.4 GHz. The firmware picks the band by signal
  strength, not always 5 GHz, and shows the signal on the screen and in the app.

## Downloads

Goal: tap a card, sound within a second, even for something not downloaded yet.

* **First part kept on the card:** the first ~30 s of every card's audio is kept on SD, so a tap
  plays at once even while Wi-Fi is still waking up.
* **Download in parts:** the rest comes in 256 KB chunks (HTTP range requests) into a `.part`
  file, with a small list of the chunks that are done. Playback reads from the part file. A
  128 kbit/s MP3 needs 16 KB/s; the box downloads at roughly 1–2 MB/s (limited by SD writes over
  SPI), so playback never catches up. If it ever does, it waits on the next chunk instead of
  stopping.
* **Survives dropouts:** a lost connection resumes at the first missing chunk. A file is renamed
  into place only when complete and checked, so a working file is never replaced by half a one.
* Expect about 1–2 minutes for a 100 MB audiobook, in the background, while it already plays.

## Phase 0: before any wire goes on

1. Read the **ESP32-C5 datasheet, Boot Configurations**: confirm GPIO 2, 3, 7, 25 and 26 are
   safe driven only by the C5 itself, and note what level each needs at reset.
2. Read the charger board's listing or schematic: CC resistors present, power path, charge
   current.
3. Flash a blink sketch to both dev boards over their own USB, so each is known good.
4. Set reader A's switches to **SPI** (`0 1`) and reader B's to **I2C** (`1 0`), and label them.

## Phase 1: bench test order

Same rule as v1: one part at a time, USB unplugged while wiring.

1. C5 + OLED (screen shows text).
2. + SD card on the shared bus (list files; play nothing yet).
3. + DAC → jack (a test tone in headphones). Then amp → speaker.
4. + reader A on the shared bus (UIDs print, screen and SD still work).
5. + I2C bus: MCP23017, knobs, jack detect, then reader B.
6. + WROVER: I2C commands, then I2S to Bluetooth headphones, then speaker mode from a phone.
7. Wi-Fi: chunked download while playing, with Wi-Fi switched off and on at the router.
8. Power: charger, buck-boost, battery (the v1 polarity check with the multimeter still
   applies), switch. One hour on battery at full volume with Bluetooth and a download running.

## Known limits

* Bluetooth headphones and box-as-speaker are not available at the same time.
* Bluetooth headphones lag the jack by about 0.2 s.
* The C5 has no free pins left (one strapping pin, output only). More buttons go on the
  MCP23017's spare inputs.
* Downloads are about 1–2 MB/s. Fine with part-by-part playback; not instant for whole files.
* Run time (estimate, 5000 mAh): around 8–12 h of playing, less with Bluetooth and the screen
  bright the whole time. To be measured in Phase 1 step 8.
